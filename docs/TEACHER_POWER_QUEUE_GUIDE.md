# 给老师的说明：Power、上限、清零与排队生成

## 先记住四句话

1. **Power 上限**是每位学员在当前教学周期可使用的总量，例如上限为 1，表示本周期最多使用 1 Power。
2. **已用额度**包括已经排队、已被供应商接单和已经完成的任务。任务刚进入队列时会先预留预计 Power，避免同一名学员连续点击占用多份额度。
3. **供应商并发**是学校账号同一时间能让 Tripo3D 或 Hyper3D 实际生成的数量；它与 Power 上限不是一回事。
4. **清零**会开启一个新的额度周期：尚未提交供应商的等待任务会取消并退回预留；已经被供应商接单的任务继续完成，但不会回写到新周期的已用额度。

## 为什么上限设为 1 后仍可能报错

将上限设为 1 只决定每名学员能否继续使用 Power，不会提高供应商账号的并发名额，也不能修复供应商余额、授权、网络或限流问题。高峰时 30 人同时点击，平台会先把任务放入本地队列；供应商只按账号合同允许的并发数逐项接单。

| 学员看到的状态 | 含义 | 老师应做什么 |
| --- | --- | --- |
| 已进入队列 | Power 已预留，正在等供应商名额 | 不要求学生重复点击，等待队列推进。 |
| 自动重试 | 供应商繁忙或暂时网络错误 | 等待下一次自动重试，不需要重新提交。 |
| 正在核对 | 平台无法确认供应商是否已经接单 | 不要重复提交；管理员先核对诊断信息。 |
| 账号暂不可用 | 供应商余额或授权需要处理 | 请 root 管理员检查余额、订阅或授权后恢复。 |
| Power 不足 | 当前周期上限已被预留/使用 | 视教学安排提高上限或清零。 |

## 清零时会发生什么

清零前系统会显示预览：受影响学员数、等待任务数、已接单任务数和预计释放的 Power。确认后：

- `waiting_provider` 与 `retry_wait` 任务会取消，不会发送给供应商，预留 Power 回到可用额度；
- 已进入供应商生成的任务不会假装取消，仍会完成或失败；
- 这些已接单任务记录在清零前的旧周期，完成、失败或退款都不改变新周期的已用 Power；
- 新周期从 `used_power=0` 开始，再按照新的上限计算可用 Power。

所以“清零后又出现旧任务完成”不是清零失效，而是系统保留了供应商已经接单的真实结果，同时隔离了它对新周期额度的影响。

## 课堂前建议

1. 确认 Tripo3D 和 Hyper3D 的账号余额、授权和合同并发。
2. 先用少量测试账号验证排队、自动重试和下载。
3. 为课堂设置合理的 Power 上限；上限与供应商并发分别检查。
4. 高峰时让学生等待状态变化，不要反复刷新或重复点击生成。
5. 需要清零时先读预览说明，再确认等待任务是否应当取消。

管理员可在运维面板查看供应商并发、有效占槽、队列长度、最老等待、暂停原因和安全告警。详细发布与故障处理见 `UNIFIED_QUEUE_P2_RUNBOOK.md`。
